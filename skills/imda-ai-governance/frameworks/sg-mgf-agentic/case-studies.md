# Case Studies — Engineering Takeaways

> ⚠ **Reference material only — not legal or regulatory advice.** See [DISCLAIMER.md](../../../../DISCLAIMER.md). Verify against the official IMDA publication and involve your risk and compliance owners.

The framework illustrates each dimension with case studies contributed by organisations. They are examples of how one organisation applied the framework, **not** requirements, and the descriptions belong to the contributors. This file records only the transferable engineering pattern from each, so a reviewer can point to precedent when proposing a design. Read the originals in the framework for context.

| Case | Section | Pattern worth reusing |
|---|---|---|
| **IMDA — OpenClaw** | §2 | Applying all four dimensions to an open-source agent platform that ships permissive by default: no mission-critical or sensitive-data use as-is; many narrow agents instead of one all-powerful one; dedicated agent identities and credentials; enforce approval through system-level controls, not prompts; attempt disallowed actions before deployment to prove restrictions work; log and attribute every action; don't leave agents unsupervised for long periods. |
| **Dayos — IT ticketing agent** | §2.1.1 | Score every action type on **severity, reversibility, and feasibility of human oversight**, and let the tier set both the reasoning strategy and the autonomy: tier 1 fully automated with periodic audits of reasoning chains; tier 2 agent diagnoses, human approves before execution; tier 3 the agent does not act at all. |
| **OCBC — source-of-wealth memos** | §2.1.2 | Bound autonomy structurally: task-level autonomy only (extract, draft, check), no self-initiation outside predefined workflow triggers, no decision authority — outputs are advisory and validated by humans at decision points. |
| **MSD — enterprise agent governance** | §2.1.2 | Risk-calibrated governance pathways by **level of agency** (lightweight → impact assessment → architecture review); a programmatic runtime policy layer at the AI gateway before enabling the highest autonomy; **contain vendor-embedded SaaS agents within their own ecosystem by default** rather than letting them act across your systems. |
| **PwC Singapore — report drafting** | §2.2.1 | Name four owners: use-case owner (appropriateness, accountable use), technology risk (controls advice), the build team (prompts, models, tools, guardrails, **managing model changes through change management, not leaving it to end users**), and subject-matter reviewers (approve outputs before reliance). |
| **Tencent — CodeBuddy coding agent** | §2.2.2 | Approval defaults tiered by action type (read free; edit per-session; shell per-project or command; network requests need approval; MCP governed by allow / ask / deny rules plus first-use trust for new servers); per-project strictness set by risk; **plain-language explanation** of proposed commands including side effects; **re-require approval when a previously allowed command pattern turns suspicious**. |
| **X0PA — recruitment agents** | §2.2.2 | In a high-impact domain keep humans at shortlisting and final selection; make outputs explainable (scores and ranking rationale); train reviewers on domain-specific failure modes; let users override and feed overrides back. |
| **Terminal 3 — payroll agent** | §2.3.1 | Scope authority in a **per-cycle signed credential** (which records, rates, thresholds, a transfer ceiling); **keep sensitive data out of the agent's context entirely** (the agent sees opaque references; computation happens in a trusted execution environment); block out-of-scope actions before execution; record a tamper-evident audit trail including blocked attempts. |
| **Cyber Sierra — questionnaire answering** | §2.3.1 | Reflection loop with both LLM-judge and metric-based checks and a **hard iteration cap that terminates the trajectory** on failure; fix stale-source errors **deterministically** with a versioned context graph instead of prompting the agent to be careful. |
| **Stability Solutions — internal vs external agents** | §2.3.1 | An external-facing agent gets stricter controls than internal ones: a **curated memory** instead of broad access, human vetting of untrusted inputs until the agent proves reliable, and explicit non-disclosure guardrails. |
| **Google x Singapore Government — computer-use agents** | §2.3.2 | Realistic test data and environments; **log and evaluate reasoning at each step** (it revealed a data-minimisation failure — the agent included extraneous personal details); test use-case-specific indirect prompt injection (the agent sometimes navigated to attacker-supplied URLs; mitigate with site allowlists); keep humans in the loop during testing of broad-action-space agents. |
| **CDL x Knovel — data access boundaries** | §2.3.2 | Test access boundaries with a **user × domain matrix**, multi-turn conversations that drift towards out-of-scope domains, comparison against authorised accounts, and attempts to get the system to "helpfully" complete redacted information. |
| **GovTech — coding assistant rollout** | §2.3.3 | Phase 1 limited to internal staff, **no MCP**, low-risk systems; build central logging, an MCP allowlist via a managed gateway, and red-team it before phase 2 widens users and tools; use OS-native sandboxes to cut approval fatigue. |
| **Workday — HR and finance agents** | §2.4.2 | Disclose AI at every interaction surface (including Slack and Teams); publish **what the agent can and cannot do**; attach reasoning, data considered, key factors and uncertainties to each recommendation in sensitive workflows. |
| **Ant International — HOP agent builder** | §2.4.3 | Let domain experts read and write the workflow spec (plain-language SOP) before it is compiled to code; confidence scores on proposed workflows; built-in verification steps with a retry cap that ends the workflow and notifies the user. |
